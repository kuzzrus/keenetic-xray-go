# Внешний аудит от 18.09.2026 — верификация находок

Два файла аудита (`keenetic-xray-go-session-audit-2026-09-18 (1).md`, 20 пунктов, и
`keenetic-xray-go-unified-audit-2026-09-18.md`, 49 пунктов — расширенная версия) были
сгенерированы сторонним инструментом **без доступа к Go toolchain, без запуска тестов
и без доступа к реальному роутеру** — чистый статический разбор исходников на
коммите `2df9932`. Часть выводов могла быть неточной, устаревшей или неверно
истолкованной.

Этот документ — результат перепроверки всех 49 пунктов против актуального кода
(включая закреплённые зависимости AWG и реальный upstream Xray-core v26.9.9,
куда это было уместно), плюс один дополнительный пункт, найденный в процессе
проверки. Для каждого: **найдено → статус проверки → что уточнилось**.

Обозначения статуса:
- **ПОДТВЕРЖДЕНО** — перепроверено напрямую по актуальному коду, находка верна.
- **ПОДТВЕРЖДЕНО (хуже)** — находка верна, но реальный масштаб/механизм серьёзнее,
  чем в исходном аудите.
- **ТРЕБУЕТ УТОЧНЕНИЯ** — механизм в основном верен, но есть важная деталь, которая
  меняет вывод (уже исправлено, не достижимо через код проекта, неверная атрибуция
  строки и т.п.).

## Установка, упаковка, релиз

### INST-01 — Мастер настройки детерминированно пропускается (не просто «может»)
**Приоритет:** P2. **ПОДТВЕРЖДЕНО (хуже формулировки аудита).**

`packaging/ipk/postinst` вызывает `internal postinst-setup` (который безусловно
создаёт заготовку `config.json`, если её нет — `internal/install/variant.go:43-65`)
**до** проверки `[ -f "$CONFIG_FILE" ]`. К моменту этой проверки файл существует
всегда. Ветка интерактивного мастера (`elif [ -e /dev/tty ]`) — мёртвый код при
установке `curl|sh` без `--sub=`/`--vless=`.

**Исправить:** решение «настроен/не настроен» брать по `len(cfg.Profiles)==0`
(уже вычисляется в `internal.go:135`), не по факту существования файла.

### INST-02 — Общие временные файлы без блокировки
**Приоритет:** P2. **ПОДТВЕРЖДЕНО**, плюс то же самое в ядре/naive-обновлениях.

`install.sh` использует фиксированный `/opt/keenetic-xray-install.ipk`.
Аналогично `internal/xraycore/xraycore.go:194-216` и
`internal/naivecore/naivecore.go:123-145` используют `dest+".keenetic-xray.tmp"`
без блокировки. Дополнительно подтверждён порядок операций: `MkdirAll` вызывается
**после** попытки скачать временный файл — при отсутствующем каталоге назначения
загрузка падает раньше, чем успевает сработать `MkdirAll`.

### INST-03 — Серверный бинарник без проверки и отката
**Приоритет:** P1. **ПОДТВЕРЖДЕНО.**

`server-install.sh`: скачивание → `chmod` → `mv` на боевой путь без checksum,
без smoke-теста, без сохранения предыдущей версии. Единственная проверка —
`systemctl is-active` уже после подмены.

### INST-04 — Проверка `/dev/tty` не гарантирует управляющий терминал
**Приоритет:** P2. **ПОДТВЕРЖДЕНО**, и это не гипотетика — комментарий в самом
`postinst:54-58` описывает реальный прошлый инцидент именно с этим паттерном для
apgrade-ветки; `server-install.sh:99` аналогичной защиты не получил вообще.

### INST-05 — Удаление пакета оставляет сетевые правила и watchdog активными
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, серьёзно.**

`prerm` → `cmdPrermCleanup` (даже с `--purge`) чистит только routes/MSS/WG-transport/DNS.
Он **никогда** не вызывает `adaptiveroute.ClearRedirect`, `l7capture.ClearRules`
или `install.SetWatchdogCron(false)` — эти функции подключены только к CLI/боту,
не к prerm. После удаления пакета: REDIRECT-правила и NFLOG остаются в iptables,
указывая в никуда, а watchdog-cron (`*/2 * * * *`) продолжает бесконечно дёргать
уже не существующий бинарник.

### REL-01 — Релиз публикуется раньше, чем готовы все артефакты
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, все 4 части.**

GoReleaser публикует релиз (`release --clean`) **до** шагов UPX/QEMU/IPK — сбой
любого из них оставляет публичный релиз без части ассетов. `checksums.txt`
считается ДО того, как собран `.ipk`, и никогда для него не расширяется.
`install.sh` вообще не проверяет контрольную сумму `.ipk` перед `opkg install`.
`ci.yml` и `release.yml` — независимые workflow без `needs:`/`workflow_run`,
то есть тег сам по себе не гарантирует прохождение тестов.

## Обновление агента и бот

### UPD-01 — Кнопка «Обновить агент» (исходная жалоба пользователя)
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, механизм точно воспроизведён.**

`selfUpdate()` (`internal/botcontrol/commands.go:1136-1197`) пишет вывод дочернего
процесса в `bytes.Buffer` через `c.Stdout, c.Stderr = &out, &out` — Go обслуживает
это через реальный OS pipe и горутину **в этом же процессе**. `Setsid`/отделение
сессии не выставлено нигде. Этот процесс — тот же самый `keenetic-xray daemon`,
который `packaging/ipk/prerm` останавливает через `S99keenetic-xray stop`
**посреди** цепочки `sh -c "curl → install.sh → opkg install → prerm → postinst →
start"`. Как только родитель гибнет, ядро закрывает читающий конец pipe; следующая
попытка **любого** процесса в этой цепочке (a install.sh, а особенно сам opkg)
написать в stdout/stderr получает SIGPIPE (поведение по умолчанию — завершение).
Ничего не перенаправляет вывод в файл вместо этого pipe.

Это не детерминированный баг на каждый клик (зависит от того, кто именно пишет
в момент остановки родителя), но исчерпывающе объясняет «раньше обновлялось,
потом стало умирать» в сочетании с тем, что установка становится тяжелее по мере
роста списка шагов постинсталляции (доустановка watchdog/ядра и т.п.) — больше
записей в лог, больше окно для гонки.

**Исправить:** вынести обновление в отдельный detached-процесс (`Setsid`),
stdout/stderr — в файл журнала, а не в pipe родителя; отдельная блокировка от
повторного клика; файл состояния (prepare/download/install/start/verify/rollback),
который новый агент дочитывает и сообщает результат в чат.

### UPD-02 — Откат зависит от уже заменённого бинарника
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, все 3 части.**

Watchdog-откат (`cmdWatchdogRestartHook`) — это команда **того же** свежеустановленного
бинарника; если новый билд вообще не запускается, путь отката недоступен. `watchPostUpdate`
считает успехом сам факт `ActivePrimary`/`ActiveBackup` в машине состояний, не
проверяя реальную работоспособность Xray/туннеля. Переустановка той же версии
тихо чистит маркер без единого уведомления в чат.

### BOT-01 — Потеря команд/результатов в очереди
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, хуже формулировки аудита.**

`Dequeue` удаляет команду из Pending и сохраняет **до** доставки HTTP-ответа —
без подтверждения агента, без повторной выдачи при потере ответа. Результаты
хранятся как единственный `LastResult`, второй результат может затереть ещё не
прочитанный первый. Хуже: если `saveLocked()` после `Dequeue` падает с ошибкой —
команда уже выкинута из памяти безвозвратно, не просто рассинхронизирована с диском.

### BOT-02 — Долгая команда режет собственную доставку результата
**Приоритет:** P2. **ПОДТВЕРЖДЕНО**, с уточнением: цитата аудита указывала не на ту
функцию (реальный self-update использует `context.Background()` и НЕ подвержен
этому конкретному багу) — но `ensureCore`/`updateCore` реально используют общий
с `Handle`+`postResult` контекст, и их «5-минутный» вложенный таймаут на деле
ограничен более коротким родительским.

### BOT-03/04/05 — Реестр роутеров, лимит callback_data, лимит длины сообщения
**Приоритет:** P2 каждый. **ПОДТВЕРЖДЕНЫ все три.**
- Удалённый через бот роутер, оставшийся в старом `cfg.Routers`, возвращается
  после рестарта control-сервера (SeedRouter не знает о ручном удалении).
- ID роутера длиной 64 символа + префикс `router:` даёт 71 байт callback_data —
  сверх лимита Telegram в 64 байта; в проекте минимум 8 мест строят такую кнопку.
- `send`/`editMessageText` шлют текст целиком без разбивки; `daemonLog` может
  вернуть до 500 строк без ограничения по байтам — превышение 4096 символов
  Telegram просто отклоняет молча (видно только в логе сервера).

## Конфигурация, демон, failover

*(этот кластер разобран мной лично, без делегирования — прямо пересекается
с текущей работой над пул-ротацией backup)*

### CFG-01 — Общий изменяемый `*Config`, гонка данных
**Приоритет:** P1. **ПОДТВЕРЖДЕНО.**

`Daemon`, `realActions` и `RouterHandler` в буквальном смысле держат один и тот же
указатель `*config.Config` (`cmd/keenetic-xray/main.go`, один раз создаётся,
передаётся всем трём). `ReloadConfig` делает `*d.cfg = *fresh` на горутине `Run`
(сериализовано с `Tick`), но обработчики бота (например `setPorts`,
`internal/botcontrol/commands.go:1089-1090`: `h.Config.Failover.SOCKSPort = ...`)
пишут в те же поля **напрямую, на своей собственной горутине**, в обход командной
очереди демона. Это настоящая гонка данных, ловится `go test -race`.

### CFG-02 — Смена портов не проверяет конфликт с внутренними слушателями
**Приоритет:** P1. **ПОДТВЕРЖДЕНО.**

`setPorts` проверяет только диапазон 1-65535 и SOCKS≠HTTP. Не проверяется
пересечение с `PretestPort`, `PretestPort+2`/`+3` (порты naive-сайдкаров,
`internal/failover/daemon.go:260-261`) или `DefaultAdaptiveRoutePort=12080`.
При дефолтном `pretest_port=11080` установка `HTTP=11082` реально коллизирует
с production naive-сайдкаром.

### FAIL-01 — Демон без primary не обслуживает команды
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, с важным смягчающим нюансом.**

`Run()` при `cfg.Primary()==nil` уходит в голый `<-ctx.Done()`, не читая
`d.commands` вообще — `Snapshot`/`ForceSwitch`/`ReloadConfig` зависают до истечения
таймаута вызывающей стороны. Смягчение: `rebindXray` (`commands.go:641-662`)
уже проверяет `Snapshot(ctx)` и при неудаче падает на `restartDaemonDetached()` —
то есть первая настройка профиля через бота не виснет навечно, а стоит одного
лишнего рестарта демона с задержкой. Отдельно подтверждено: тикер здоровья
создаётся один раз при старте `Run()` и не пересоздаётся при смене
`CheckIntervalSeconds` через `ReloadConfig` — новый интервал попадает в
`d.machine.cfg`, но реальный тикер продолжает стрелять по старому расписанию
до рестарта процесса.

### FAIL-02 — Ошибки переключения роли игнорируются, состояние идёт дальше
**Приоритет:** P1. **ПОДТВЕРЖДЕНО**, плюс уточнение, которое меняет оценку риска.

`_ = m.actions.SwitchLiveTo(ctx, RoleBackup)` в `state.go` — ошибка отброшена,
состояние машины переходит в `Cooldown`→`TestingRecovery` независимо от реального
результата. Хорошая новость: `realActions.SwitchLiveTo` пишет `a.liveRole = role`
**только** после успешного `a.prod.Restart()` (`daemon.go:372-375`) — то есть
`Snapshot().LiveRole` в случае неудачи НЕ соврёт, что мы на backup. Но
`Snapshot().State` при этом уже покажет `TESTING_RECOVERY` — расхождение между
`State` и `LiveRole` ровно в тот момент, когда переключение реально не удалось
(например, пишет плохой конфиг, xray не стартует) — пользователь в статусе бота
видит «тестируем возврат на primary», хотя реально нет рабочего соединения вообще.

### FAIL-03 — Утечка соединений в health-пробнике
**Приоритет:** P2. **ПОДТВЕРЖДЕНО, точный механизм.**

`probeOnce` (`internal/xrayctl/probe.go:82-115`) создаёт **новый** `http.Transport`
на каждый вызов, без `IdleConnTimeout` (zero-value = без ограничения) и без
`CloseIdleConnections()`. Если сервер здоровья держит keep-alive, каждый пробник
может оставить одно постоянное соединение+горутину, которые никогда не закроются
сами. При интервале проверок в секундах на многомесячном аптайме — реальная
медленная утечка.

### XR-01 — Валидатор профиля расходится с реальным Xray v26.9.9
**Приоритет:** P2. **ПОДТВЕРЖДЕНО однозначно (h2/http), правдоподобно (REALITY).**

Прямая сверка с реальным upstream-исходником `XTLS/Xray-core@v26.9.9`
(`infra/conf/transport_internet.go`): транспорт `h2`/`h3`/`http` **удалён**
из Xray — `case "h2", "h3", "http": return "", errors.PrintRemovedFeatureError(...)`.
Валидатор этого проекта (`internal/config/profile.go:162`) всё ещё принимает
`h2`/`http` как валидную сеть — профиль пройдёт локальную проверку и сохранится,
а реальный xray-core откажется стартовать. REALITY с пустым `ShortID`
(`profile.go:172`, безусловный отказ) — правдоподобно, но не перепроверено
против реального REALITY-сервера с пустым списком short-id.

## AmneziaWG

*(верифицировано против реального закреплённого форка `kuzzrus/amneziawg-go@58a3db1`
и реального upstream `XTLS/Xray-core@v26.9.9` — не только против этого проекта)*

### AWG-01 — Нет проверки, что установленное ядро реально поддерживает AWG
**Приоритет:** P1. **ПОДТВЕРЖДЕНО.**

`Ensure()`/`coreVersionKnownWrong()` сравнивают только строку `Xray X.Y.Z` —
патч никогда не трогает эту строку, значит patched и vanilla сборки одного тега
неотличимы. Весь путь активации AWG-профиля (`setSlotSource` →
`ResolveSourcePinned` → `ParseAmneziaWGURI` → `validateAmneziaWG()`) проверяет
только непустоту приватного/публичного ключа — вообще никакой проверки
возможностей бинарника.

### AWG-02 — Dual-stack `Address` ломается
**Приоритет:** P2. **ПОДТВЕРЖДЕНО.**

`applyAmneziaWGInterfaceField`'s `"address"` кейс копирует значение как есть
(в отличие от соседнего `"dns"` кейсом, который правильно использует
`splitTrimmedCSV`). `Address = 10.8.1.2/32, fd00::2/128` превращается в один
элемент массива с запятой внутри — простое несоответствие с DNS-кейсом в той же
функции, тривиально чинится.

### AWG-03 — Некорректный DNS вызывает panic в Xray
**Приоритет:** P1. **ПОДТВЕРЖДЕНО**, с уточнением атрибуции: это поведение
немодифицированного апстрима (`NewClient` в `proxy/wireguard/client.go`,
`netip.MustParseAddr` без проверки), патч AWG его не касается и не создавал —
но этот проект тоже не валидирует DNS при импорте `.conf`, так что путь
"кривой DNS в .conf → panic всего процесса xray" реально открыт.

### AWG-04 — `Jmin > Jmax` → unsigned underflow → потенциальный OOM
**Приоритет:** P1. **ПОДТВЕРЖДЕНО точной сверкой с реальным кодом форка.**

`device/uapi.go` в `kuzzrus/amneziawg-go@58a3db1` парсит `Jmin`/`Jmax` независимо
через `ParseUint`, без взаимной проверки. `device/noise-protocol.go`'s
`JunkPackets()`: `make([]byte, min+fastrandn(max-min))` — при `Jmin>Jmax`
беззнаковое вычитание даёt число, близкое к 2^32. Реальный риск многогигабайтной
аллокации на роутере с 128-512 МБ памяти. Нужен апстрим-фикс в форке
(`Jmin<=Jmax`, ограничение размера/количества мусорных пакетов) + обновление
закреплённого коммита в обоих патчах (`v26.9.9` и `v26.3.27`).

### AWG-05 — Устройство не закрывается при ошибке `IpcSet`/`Up`
**Приоритет:** P2. **ПОДТВЕРЖДЕНО**, но это немодифицированный апстрим-код
(влияет одинаково на обычный WireGuard), не специфика AWG-патча.

### AWG-06 — Диагностический CGO-флаг может попасть в production-релиз
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, реально не закрыто прямо сейчас.**

Это моя собственная недавняя работа в этой же сессии — нашёлся пробел: для
подтверждённого тега (`v26.9.9`) патч и целевой релиз считаются правильно
(`xray-core/v26.9.9`), но шаг `CGO_ENABLED`/установка cross-toolchain в
`.github/workflows/xray-core.yml` завязан **только** на сырой `inputs.awg_dev`,
а не на итоговый `apply_patch`/подтверждённость тега. Повторный dispatch
`xray_version=v26.9.9, awg_dev=true` (а такая комбинация реально использовалась
при отладке) соберёт arm64 с `CGO_ENABLED=1` и залил бы это в реальный
production-релиз через `--clobber`. mipsle не затронут. **Нужно почини́ть**:
завязать CGO-диагностику на `apply_patch`/подтверждённость тега, а не на голый
`awg_dev`.

### AWG-07 / AWG-08 — reserved+AWG коллизия / нет AWG на серверном inbound
**Приоритет:** P2 каждый. **ПОДТВЕРЖДЕНЫ, оба — не достижимы через код этого проекта.**

AWG-07: `AmneziaWGParams` не имеет поля `reserved`, `buildAmneziaWGOutbound` его
никогда не пишет — коллизия возможна только в ручном JSON-конфиге. AWG-08: патч
действительно не переносит 25 AWG-полей в `server.go`, но этот проект никогда не
строит AWG-inbound (только egress, роутер как клиент) — ограничение реально, но
не задевает текущий функционал.

## Адаптивная маршрутизация и L7/SNI

### AR-01 — Подтверждение по тому же снимку conntrack, до применения правила
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, самая серьёзная находка кластера.**

Численный пример аудита воспроизведён буквально шаг за шагом:
`ClrFast`→`ClrJudge` в одном проходе одного и того же `flows`-среза подтверждают
адрес как «OK» на 6 часов **до** того, как REDIRECT/ipset для него вообще применён.
Плюс: после REDIRECT TCP-клиента реально терминируется на локальном Xray —
пакеты от локального стека не доказывают, что удалённый сайт отвечает.

### AR-02 — Один общий ipset на TCP/80, TCP/443, UDP/443
**Приоритет:** P2. **ПОДТВЕРЖДЕНО.** `Action` несёт только IP+TTL, протокол/порт
нигде не участвует в ключе решения.

### AR-03 — Укрупнение блоков расширяется без проверки соседей
**Приоритет:** P1 в аудите → **ТРЕБУЕТ УТОЧНЕНИЯ: это уже исправлено.**

Пороги подтверждены (`BlockThreshold=4`, потолок `/18`), но /18 — это жёсткий,
уже вшитый потолок (`knownRangeAcceptable`), а не «может расшириться». Это
результат PR #179/#180 из этой же кодовой базы (инцидент с Google/Facebook
диапазонами в сентябре), задокументированный как осознанный компромисс, а не
забытый баг. Описание масштаба (256 / 16384 адресов) верно, но подача как «живой
незакрытый P1» — нет.

### AR-04 — Watch не сбрасывается при возобновлении ответов
**Приоритет:** P2. **ПОДТВЕРЖДЕНО, сценарий аудита воспроизведён** (с реальными
дефолтами `WatchTTL=8s` вместо иллюстративных 10s в аудите — механизм тот же).
Существующий тест правда не проверяет сброс Watch, только отсутствие действия
в момент восстановления.

### AR-05 — Нет отдельной проверки восстановления DIRECT
**Приоритет:** P2. **ПОДТВЕРЖДЕНО**, с уточнением: полностью бесконечное продление
требует нестандартного `OKTTL≤3ч` (дефолтные кнопки бота — 6/12/18/24ч), но путь
достижим через CLI/API вне кнопок.

### AR-06 — Исключения не ретроактивны, не переживают live-изменение настроек
**Приоритет:** P2. **ПОДТВЕРЖДЕНО.** `clsCfg` (в т.ч. RU-исключения) строится один
раз и не пересобирается при изменении `disable_russian_ip_exclusion` без рестарта.

### AR-07 — SNI одного домена открывает туннель для всего IP
**Приоритет:** P2. **ПОДТВЕРЖДЕНО, не переисправление старого бага** — отдельная,
реально открытая проблема (не связана с уже исправленным несоответствием
hostname/IP-decision из истории проекта).

### AR-08 — `block_threshold=0` не значит «выключено»
**Приоритет:** P2. **ПОДТВЕРЖДЕНО буквально**: обработчик команды пишет `0` и
рапортует «отключено», `EffectiveBlockThreshold()` трактует `0` как «дефолт (4)».
Кнопка бота шлёт `-1` и работает правильно — баг достижим только через CLI/API
напрямую со значением `0`.

### AR-09 — Reconcile отменяет аварийный fail-open обратно в DIRECT
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, серьёзнее, чем в аудите.**

`failedOpen` — чисто локальная переменная одной горутины; `reconcileAdaptiveRoute`
проверяет только `Enabled`, ничего не знает про реальное здоровье туннеля, и
запускается каждые 2 минуты **плюс** по SIGUSR1 от ndm netfilter-hook. Даже
**успешно** снятый REDIRECT (туннель реально мёртв) будет молча возвращён
следующим plановым reconcile или пересборкой firewall — максимум через 2 минуты
после того, как сработала защита.

### AR-10 — CLI flush не переживает живой процесс classifier
**Приоритет:** P2. **ПОДТВЕРЖДЕНО** собственными комментариями кода: у CLI нет
`.reset`-маркера, который использует бот, и который по документированной причине
существует именно потому, что «просто удалить файл состояния ненадёжно, пока
демон работает».

### L7-01 — L7 работает без готового dataplane, игнорирует `RouteIface`
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, все 3 части.** L7 не проверяет
`AdaptiveRoute.Enabled`; ошибка `AddIP` отбрасывается, а conntrack-запись всё
равно удаляется (рвёт рабочее соединение зря); домены собираются из всех
списков без учёта `RouteIface()`, хотя эта функция существует и используется
в других местах проекта.

### L7-02 — NFLOG теряет остальные сообщения датаграммы, не самовосстанавливается
**Приоритет:** P2. **ПОДТВЕРЖДЕНО.** Ошибка `syscall.Read` завершает горутину
захвата навсегда; reconcile восстанавливает правила firewall, но не читающую
горутину.

## Firewall, DNS, локальный WG, аддоны

### FW-01 — Очистка правил по широким сигнатурам, ошибки проглатываются
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, все 3 части.** Приятная находка: в проекте уже
есть готовый `unquote()`-хелпер (`internal/keenetic/wireguard.go:430-435`) для
похожей проблемы с NDM-полями — просто не применён к пути очистки
iptables-комментариев. Собственные тестовые фикстуры симулируют **неэкранированный**
вывод `-S`, поэтому тесты эту проблему не ловят.

### DNS-01 — Потеря владения DNS-записями при смене/отключении
**Приоритет:** P1. **ПОДТВЕРЖДЕНО**, точный механизм: `dnsPreset` делает полный
сброс `cfg.DNS` **до** вычисления «managed»-множества — старый custom-адрес
выпадает из владения раньше, чем должен быть удалён. `dnsOff` сохраняет пустой
конфиг раньше `ClearDNS` — при неудаче очистки следующий reconcile уже не видит,
что удалять.

### WG-01 — Пересоздание WG-ключа не долетает до живого Xray
**Приоритет:** P1. **ПОДТВЕРЖДЕНО, точная трассировка.** `routerReconcileLoop`
работает с отдельной копией конфига и никогда не вызывает `Daemon.ReloadConfig`
(единственный реальный путь к живому xray-core) — новый публичный ключ пишется
в `config.json`, но уже запущенный WG-inbound держит старый ключ пира до
следующей несвязанной команды или ручного рестарта.

### ADD-01 — Значения настроек пишутся в shell-конфиг без экранирования
**Приоритет:** P1. **ПОДТВЕРЖДЕНО** (экранирование отсутствует буквально,
`ISP_INTERFACE` и несколько Susanin-полей не валидируются вообще). Эксплуатируемость
зависит от того, действительно ли сторонние init-скрипты (не в этом репозитории)
делают `source` этих файлов — правдоподобно по собственным комментариям кода,
но не проверяемо изнутри этого репозитория.

### ADD-02 — DNS-аддоны перезаписывают чужой конфиг, игнорируют ошибку отвязки
**Приоритет:** P2. **ПОДТВЕРЖДЕНО**; в коде это осознанный компромисс
(явный комментарий), не оплошность — но риск («Keenetic указывает на
несуществующий резолвер») от этого не меньше.

## Пресеты и подписки

### PRE-01 — IP-компаньон пресета не получает интерфейс/exclusive
**Приоритет:** P2. **ПОДТВЕРЖДЕНО**, и найдена дополнительная деталь: даже ручной
обход в `setup.go` чинит только `Interface`, но никогда `Exclusive` — флаг
`--exclusive` для CIDR-половины пресета не работает вообще нигде в проекте.

### PRE-02 — Целостность авто-обновления пресетов (6 под-пунктов)
**Приоритет:** P2 в аудите (по сути ближе к P1 по характеру риска).
**ПОДТВЕРЖДЕНО все 6 частей**, один пункт хуже, чем предполагал аудит: при ошибке
записи файла строка **не** «падает обратно на встроенный дефолт», как
предполагалось — она просто исчезает из индекса целиком (и для оверлейных, и для
встроенных пресетов) до следующего успешного обновления. Путь traversal через
`Name` в `filepath.Join` реален, но требует скомпрометированного источника
манифеста (по умолчанию — репозиторий проекта).

### PRE-03 — Генератор пресетов игнорирует ошибки чтения/записи
**Приоритет:** P2. **ПОДТВЕРЖДЕНО, все 3 части**, включая реальный риск паники на
`nil` `*http.Request` при отброшенной ошибке `NewRequest`.

### SUB-01 — Обрыв Scanner тихо обрезает список подписки
**Приоритет:** P2. **ПОДТВЕРЖДЕНО.** Нужна строка длиннее 64КБ (нетипично для
`vless://`, но ничем не ограничено на стороне сервера подписки), эффект — тихая
потеря профилей, читается как обычное обновление.

## Дополнительная находка (не из аудита)

### SETUP-VPN — Неинтерактивный `setup` не распознаёт `vpn://`
**Приоритет:** P2 (низкий риск, тривиально чинится). **Найдено в процессе
верификации.**

`cmd/keenetic-xray/setup.go` (строки 145, 374) использует собственную ручную
проверку префикса (`vless://`/`naive+`), не зная про `vpn://` — хотя
`config.ParseProfileURI`, вызываемый сразу после, уже поддерживает AmneziaWG.
Это третий по счёту независимый пропуск такого рода в проекте (после аналогичных
находок в мастере бота и в `subscription/resolve.go` этой же сессией).

## Что не проверялось / ограничения этой верификации

Как и исходный аудит, эта верификация — чтение исходников, а не запуск.
`go test`/`go test -race`/`go vet`/реальная сборка и реальный роутер не
использовались для проверки НОВЫХ находок из этого документа (хотя изменения,
уже внесённые в этой сессии до аудита, отдельно прогонялись через полный
`go test ./...`). Часть выводов (особенно UPD-01, AR-01, AR-09) обоснованы очень
детальной трассировкой кода и должны хорошо предсказывать реальное поведение,
но финальное подтверждение — только на живом роутере с логами.
