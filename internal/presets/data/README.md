# `internal/presets/data/` — готовые списки для маршрутов

Курируемые списки доменов и IPv4-подсетей по сервисам, из которых бот и
CLI собирают маршруты на роутере (📍 Маршруты → 📦 Готовые списки,
`keenetic-xray routes preset …`). Файлы этого каталога вшиваются в
роутерный бинарь через `//go:embed` в `internal/presets`.

## Что здесь лежит

| файл | чем является | правится руками? |
|---|---|---|
| `sources.json` | вход генератора: список пресетов (сервис → теги Geo-Aggregator + провайдеры CIDR), лимиты, пороги дрейфа | **да** |
| `<name>.lst` | домены пресета, по одному в строке | нет, генерируется |
| `<name>-ip.lst` | IPv4-подсети (CIDR) пресета | нет, генерируется |
| `manifest.json` | опись всех пресетов: имя, категория, вид, число записей, `rev` (sha256 содержимого) | нет, генерируется |

`<name>.lst` / `<name>-ip.lst` / `manifest.json` **перезаписываются целиком**
при каждом прогоне `cmd/geo-gen` — ручные правки в них потеряются. Всё,
что настраивается руками, живёт в `sources.json`.

## Как обновляются

`.github/workflows/geo-update.yml` раз в сутки (и по кнопке
*Run workflow*) запускает `go run ./cmd/geo-gen`, который:

1. тянет каталог Geo-Aggregator (`db/catalog.json`) и по нему —
   `sourceN/<tag>.txt` для каждого сервиса (домены);
2. тянет `lord-alfred/ipranges/<provider>/ipv4.txt` (+ отдельные URL из
   `cidr_extra`, например официальный список Telegram) — подсети;
3. каждую строку прогоняет через `config.ClassifyRouteEntry` — тот же
   фильтр, что применяет роутер к записи, введённой руками (никаких
   `*`, IPv6, приватных диапазонов, IDN);
4. домены дедуплицирует и сортирует; при переборе лимита оставляет
   более «корневые» (`paypal.com` важнее, чем `paypal.com.hk`);
5. подсети агрегирует (склеивает соседей, выкидывает вложенные —
   `github` ~6000 → несколько сотен), при переборе лимита оставляет
   самые крупные блоки;
6. **предохранитель:** если свежий список усох более чем вдвое или
   раздулся более чем вдвое против прежнего (и в прежнем было
   ≥ `min_keep` записей) — берётся прежний файл, в отчёте пишется
   причина. Пустой ответ всех источников — тоже держим прежний.

Если разом меняется больше половины файлов — генератор отработал, но
workflow открывает PR вместо коммита в `main` (признак того, что
поменялся формат вверх по течению и нужны глаза).

## Добавить сервис

В `sources.json` скопировать строку в массиве `presets`, задать
`name` / `title` / `category`, в `ga_tags` указать id сервиса из
каталога Geo-Aggregator (можно несколько кандидатов — возьмётся первый
существующий). `cidr_providers` добавлять только если блок провайдера —
это действительно инфраструктура сервиса и он вменяемого размера
(контентные/прикладные сервисы, не облака целиком). Прогнать
`go run ./cmd/geo-gen` и закоммитить и `sources.json`, и новые файлы.

## Источники и лицензии

- **Geo-Aggregator** — https://github.com/Ground-Zerro/Geo-Aggregator
  (домены; сам агрегирует ~7 общедоступных списков).
- **lord-alfred/ipranges** — https://github.com/lord-alfred/ipranges
  (CIDR по провайдерам; собирается из официальных публикаций провайдеров).
- **Telegram** — https://core.telegram.org/resources/cidr.txt
  (официальный список подсетей).

Списки настолько полны, насколько полны эти источники. Тонкий список
(1–2 домена) обычно означает, что у сервиса и правда один корневой
домен — Keenetic сам покрывает поддомены. Дополнить можно вручную:
`keenetic-xray routes add <список> <домены…>`.
